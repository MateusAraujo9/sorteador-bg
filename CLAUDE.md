# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sorteador de Boardgames — a Portuguese-language web app for registering board games and randomly drawing one to play. Express backend in a small layered structure, a modular vanilla-JS frontend (no framework/bundler), SQLite/libSQL (via `@libsql/client`) as the datastore — a local file with zero config, or Turso (hosted libSQL) in production. Cookie-based session auth scopes every board game to its owning user. No build step, no linter. Backend has an integration test suite (`node:test`, see Testing below) — the frontend does not.

## Commands

```
npm install   # install dependencies (express, cors, plus eslint/eslint-plugin-security as devDependencies)
npm start     # run the server (node server.js), serves on http://localhost:3000
npm run dev   # identical to npm start — no watch/reload configured
npm test      # run the backend test suite (node --test), see Testing below
npm run lint  # run eslint, see "Code quality: ESLint" below
```

There is no build process in this repo.

## Architecture

### Backend (layered, not a single file)

- `server.js` — entry point only: creates the app via `src/app.js` and calls `.listen()`.
- `src/app.js` — Express app factory (`createApp()`): wires middleware (`cors`, `express.json`, cookie parsing, static `public/`) and mounts `src/routes`.
- `src/routes/auth.routes.js` — mounted at `/api/auth`. `register`/`login`/`logout`/`verify-email`/`resend-verification`/`forgot-password`/`reset-password` are public; `GET`/`PATCH /me` require `requireAuth`.
- `src/routes/boardgames.routes.js` — mounted at `/api/boardgames`. The whole router runs behind `requireAuth` (`router.use(requireAuth)`) — every boardgame endpoint requires a logged-in user.
- `src/routes/admin.routes.js` — mounted at `/api/admin`. The whole router runs behind `requireAuth` *and* `requireAdmin` (`router.use(requireAuth, requireAdmin)`) — every admin endpoint requires a logged-in admin.
- `src/routes/bgg.routes.js` — mounted at `/api/bgg`. Behind `requireAuth` plus its own rate limiter (30/15min, generous — this isn't a brute-forceable endpoint, the limit is just to stop runaway/accidental hammering of a third-party API through our server).
- `src/controllers/auth.controller.js` — register/login/logout/me/updateProfile/verifyEmail/resendVerification. Never returns `passwordHash` to the client (`toPublicUser`).
- `src/controllers/boardgames.controller.js` — request/response handling and input validation; always scopes reads/writes to `req.user.id`.
- `src/controllers/boardgameLinks.controller.js` — CRUD for a boardgame's documents (manual, expansions...). Every handler first calls `boardgamesRepository.findByIdForUser(gameId, req.user.id)` and `404`s if that fails, before touching `boardgameLinksRepository` — links are a nested resource, so ownership is always checked through the parent game, never by trusting `gameId` alone.
- `src/controllers/admin.controller.js` — `listUsers` (all users + each one's active game count, batched via `boardgamesRepository.countByUser()`, not one query per user) and `updateUserRole` (`PATCH`, body `{ role }`, `role` must be `'user'`/`'admin'`). `updateUserRole` refuses to let an admin change their *own* role (`400` if `req.params.id === req.user.id`) — a deliberate guard so an admin can never accidentally strip their own access with nobody left to undo it.
- `src/controllers/bgg.controller.js` — `search`/`getDetails`, both thin wrappers around `src/utils/bgg.js`. Check `process.env.BGG_API_TOKEN` upfront and respond `503` (feature not configured on this server) before ever calling the client, rather than letting every request pay the round-trip to `bgg.js` just to get the same "not configured" error back — that error is only a defense-in-depth fallback for other callers now. Any other thrown error (BGG down/timed out/schema surprise) is caught and answered `502` rather than falling through to the generic `500` handler, since a flaky third-party API is an expected failure mode here, not a bug. `search` also `400`s on an empty `q` and caps results to 15.
- `src/middleware/requireAuth.js` — reads the `sid` cookie, resolves it to a session then a user via the repositories below, and sets `req.user`; responds `401` otherwise.
- `src/middleware/requireAdmin.js` — synchronous (no repository call — `req.user` is already loaded by `requireAuth`, which must run first), `403`s unless `req.user.role === 'admin'`.
- `src/middleware/cookies.js` — minimal hand-rolled `Cookie` header parser (no `cookie-parser` dependency) populating `req.cookies`.
- `src/middleware/rateLimit.js` — minimal hand-rolled fixed-window rate limiter (no `express-rate-limit` dependency), keyed by `${route}:${req.ip}` in an in-memory `Map` with a periodic sweep. Applied to `/api/auth/register` (5/hour), `/api/auth/login` (10/15min), `/api/auth/verify-email` (10/15min), `/api/auth/resend-verification` (5/hour), `/api/auth/forgot-password` (5/hour), and `PATCH /api/auth/me` (10/15min, added after CodeQL's `js/missing-rate-limiting` flagged it as the one sensitive auth endpoint — password change via `currentPassword` — without a brute-force guard, unlike every other one) in `auth.routes.js`. Relies on `app.set('trust proxy', 1)` in `app.js` for `req.ip` to reflect the real client behind a reverse proxy — without it, every request behind the same proxy shares one bucket. Short-circuits to `next()` immediately when `NODE_ENV === 'test'`, since the integration tests register/log in far more times per IP than any real client would in the same window — the actual counting/blocking logic is still exercised directly, bypassing this guard, by `tests/rateLimit.test.js` (that file deliberately doesn't set `NODE_ENV=test`, see Testing below).
- `src/utils/password.js` — password hashing with Node's built-in `crypto.scrypt` (salt + hash, `timingSafeEqual` compare) — no `bcrypt` dependency.
- `src/utils/mailer.js` — `sendPasswordResetEmail(to, resetUrl)` and `sendVerificationEmail(to, code)`, both via Brevo's transactional email **HTTP API** (`fetch`, no dependency), not SMTP — outbound SMTP ports (465/587) are commonly blocked on free-tier hosts (confirmed on Render: a Gmail-SMTP version of this hung indefinitely there, worked fine locally). Uses `BREVO_API_KEY`/`BREVO_SENDER_EMAIL` env vars; each call has a 15s `AbortSignal.timeout` so a Brevo outage fails loudly instead of hanging the request. Both emails share the same felt/cream HTML layout (inline styles, web-safe font stacks only — `SERIF`/`SANS`/`MONO` — since email clients strip custom fonts); the verification one shows the 4-digit code large and letter-spaced instead of a CTA button. Both functions return immediately, without calling Brevo, when `NODE_ENV === 'test'` — tests read the generated code/token straight from the database instead (see Testing below), so they need neither network access nor a real `BREVO_API_KEY`.
- `src/utils/bgg.js` — thin client for BoardGameGeek's XML API2 (`https://boardgamegeek.com/xmlapi2`), used to auto-fill the register form. `searchGames(query)` hits `/search?type=boardgame`; `getGameDetails(id)` hits `/thing?id=`. **Requires `BGG_API_TOKEN`** — BGG rolled out mandatory app registration + `Authorization: Bearer <token>` on the XML API (register at `boardgamegeek.com/applications/create`); `fetchBgg()` throws immediately with an actionable message if the env var is unset, rather than sending an unauthenticated request that BGG would just `401`. (This was discovered the hard way: the API used to be genuinely public/keyless, initial testing got a uniform `401` across the whole domain including from a normal home network, which looked like a Cloudflare IP block at first — it wasn't.) Both parsing functions use `fast-xml-parser` (the one dependency added specifically for this — hand-rolling XML parsing via regex is a well-known footgun, unlike the other "avoid a dependency" cases elsewhere in this codebase). Sends a descriptive `User-Agent` header too. **The XML-parsing logic is exported and unit-tested against hand-written fixture XML** (`parseSearchXml`/`parseThingXml`, see `tests/bgg.test.js`) matching BGG's documented schema — live end-to-end correctness still depends on whoever runs this having a valid `BGG_API_TOKEN`, which CI/tests never do (see Testing below). `getGameDetails` prefers `playingtime`, falling back to `maxplaytime` when `playingtime` is `0` (many BGG entries leave it unset); takes the first `boardgamecategory` link as the single `category` string, since this app has one free-text category field, not BGG's multi-category/mechanic model.
- `src/utils/asyncHandler.js` — wraps an async Express handler so a rejected promise reaches `next(err)` instead of crashing unhandled (Express 4 doesn't do this automatically). Every controller/middleware function that awaits a repository call is wrapped in this.
- `src/data/db.js` — the single shared `@libsql/client` connection, used by every repository. Picks its target from env vars: if `TURSO_DATABASE_URL` is set, it connects to that (Turso, with `TURSO_AUTH_TOKEN`); otherwise it falls back to a local file — `DB_FILE` if set (an absolute or relative path, resolved with `path.resolve`), otherwise the default `data/boardgames.db` (auto-created, zero config). `DB_FILE` exists solely so the test suite can point every test file at its own throwaway temp file instead of touching `data/boardgames.db` or Turso — see Testing below. **All repository calls are async** — `db.execute({ sql, args })` returns a promise resolving to `{ rows, rowsAffected, ... }`, not the synchronous `node:sqlite` shape used earlier in this project's history.
- `src/data/migrate.js` — `runMigrations()`, the single place schema is created/evolved (all `CREATE TABLE IF NOT EXISTS` + the `boardgames.userId`/`boardgames.deletedAt`/`users.emailVerifiedAt`/`users.role` column self-migrations via `PRAGMA table_info`). Called once from `server.js` before `app.listen()` — repositories themselves no longer create tables at require-time. The `users.emailVerifiedAt` self-migration also does a **one-time backfill** in the same `if` block (`UPDATE users SET emailVerifiedAt = createdAt` — only runs the moment the column is first added, never again): without it, every account created before the email-verification feature existed would suddenly look unverified and get locked out of login after deploy. The `users.role` self-migration follows the identical pattern for the admin feature: adds `role TEXT NOT NULL DEFAULT 'user'`, then — only inside that same `if`, so it's also strictly one-time — promotes whichever user has the earliest `createdAt` (tie-broken by SQLite's implicit `rowid`, i.e. true insertion order) to `role = 'admin'`. **This backfill alone isn't enough**: `runMigrations()` runs once at server startup, before any HTTP request (and therefore before any registration) is possible, so on a genuinely fresh database the `users` table is still empty at that point and the backfill's subquery matches nothing. `usersRepository.create()` is the other half — it does `SELECT COUNT(*) FROM users` first and assigns `role: 'admin'` itself when the count is `0`, i.e. for whichever registration happens to be the very first one. The two mechanisms don't overlap in practice: the migration backfill is what makes the *already-existing* production account an admin the moment this feature deploys; `create()`'s check is what makes the *first-ever* registration on a brand-new database (nothing to backfill yet) become admin instead. Every other registration, on either kind of database, sees `COUNT(*) > 0` and gets `'user'`.
- `src/data/usersRepository.js` — `users` table (id, name, email UNIQUE, passwordHash, createdAt, emailVerifiedAt, role). `emailVerifiedAt` is `NULL` until `markVerified(id)` sets it (called once, from `verifyEmail`) — `requireAuth`-gated routes never need to check it directly, since an unverified user can never obtain a session in the first place (see Auth model below). `role` is `'user'` or `'admin'` — unlike `deletedAt`/`emailVerifiedAt`, `create()` does **not** just rely on the column's `DEFAULT 'user'`; it explicitly checks `SELECT COUNT(*) FROM users` first and sets `role: 'admin'` when the table is still empty (see migrate.js above for why this check exists alongside the migration backfill). `listAll()` (all users, `createdAt ASC`) and `updateRole(id, role)` back the admin panel — see `admin.controller.js` above.
- `src/data/sessionsRepository.js` — `sessions` table (token, userId, createdAt, expiresAt). Sessions last 30 days (`SESSION_TTL_MS`); `findValid` lazily deletes expired rows. `removeAllForUser(userId)` is used by password reset to log out every existing session once the password changes.
- `src/data/passwordResetsRepository.js` — `password_resets` table (token, userId, createdAt, expiresAt), same shape/pattern as sessions but with a 1-hour TTL (`RESET_TTL_MS`).
- `src/data/emailVerificationsRepository.js` — `email_verifications` table (userId PRIMARY KEY, code, createdAt, expiresAt, attempts), one row per user (a resend **replaces** the row via `INSERT ... ON CONFLICT(userId) DO UPDATE`, resetting `attempts` to 0) rather than accumulating old codes like `password_resets` does with tokens. `code` is a 4-digit string (`crypto.randomInt(0, 10000)`, zero-padded) with a 15-minute TTL (`CODE_TTL_MS`) — deliberately much shorter than the password-reset link's 1 hour, since a 4-digit space is small enough that a short window matters. `findByUserId` lazily deletes on expiry (same pattern as `sessions`/`password_resets`). `MAX_ATTEMPTS` (5) is enforced in the controller, not here — once hit, the code is deleted and the user must request a new one via resend. This attempt cap plus the 15-minute TTL plus the route-level rate limiters (`rateLimit.js`) are the three layers guarding a keyspace of only 10,000 possible codes — don't remove any one of them without compensating elsewhere.
- `src/data/boardgamesRepository.js` — `boardgames` table, scoped by `userId` on every read/write (`readAllByUser`, `findByIdForUser`, `randomOneByUser`, `update(id, userId, fields)`, `remove(id, userId)`). `readAllByUser` and `randomOneByUser` both attach each game's `links` array (batched via `boardgameLinksRepository.listByBoardgameIds`, not one query per game). `remove` is a **soft delete**: it sets `deletedAt` to the current timestamp instead of deleting the row, and every read (`readAllByUser`, `findByIdForUser`, `update`, `randomOneByUser`) filters on `deletedAt IS NULL` by default, so a soft-deleted game and its ownership gate (`findByIdForUser`) disappear from the app immediately. `readAllByUser(userId, { includeDeleted })` is the one exception — passing `includeDeleted: true` drops that filter so soft-deleted games are returned too (used by the "Coleção" tab's "Incluir excluídos" filter, see `main.js` below). `restore(id, userId)` is the inverse of `remove`: it clears `deletedAt` (`WHERE ... AND deletedAt IS NOT NULL`, so restoring an already-active game is a no-op 404, mirroring `remove`'s own idempotency guard). `boardgame_links` rows are deliberately left in place, neither soft- nor hard-deleted — they become unreachable once the parent game is gone (every link handler checks `findByIdForUser` first), so they're orphaned-but-inert rather than cascaded, and reappear automatically once the parent is restored. `countByUser()` is the one function not scoped to a single `userId` — it's for the admin panel, returns `{ userId, count }` for every user with at least one active (non-deleted) game in a single grouped query, not one `COUNT` per user.
- `src/data/boardgameLinksRepository.js` — `boardgame_links` table (id, boardgameId, label, url, createdAt): a game's documents (rules PDF, expansions...). Deliberately a separate table rather than a column, since a game can have any number of them.
- `data/boardgames.db` — the local SQLite/libSQL datastore file, used only when `TURSO_DATABASE_URL` is unset. Not committed to git (see `.gitignore`) — it holds real account data once you register a user.
- `.env` (not committed) / `.env.example` (committed, empty template) — `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, `BGG_API_TOKEN`. Loaded via Node's built-in `process.loadEnvFile()` in `server.js` (no `dotenv` dependency); silently skipped if no `.env` file exists, which is the normal case in local dev.

When adding a boardgame endpoint: add a repository function if new data access is needed (accepting `userId`, `async`, using `db.execute`), a controller function wrapped in `asyncHandler` that validates input and shapes the response, and a route that wires it up — in that order. New authenticated endpoints outside `/api/boardgames` should use the `requireAuth` middleware the same way `auth.routes.js` does for `/me`.

### Auth model

- Session tokens are random 32-byte hex strings, stored server-side in the `sessions` table and set client-side as an `httpOnly`, `sameSite: lax` cookie named `sid` (see `setSessionCookie` in `auth.controller.js`). `secure` is derived from `req.secure` (not `NODE_ENV`) — combined with `app.set('trust proxy', 1)` in `app.js`, this means the cookie is automatically marked `Secure` whenever the request actually arrived over HTTPS (directly or via a reverse proxy's `X-Forwarded-Proto`), and never marked `Secure` over plain HTTP (so local dev over `http://localhost` keeps working). Don't switch this back to an env-var check — it's a footgun if the var is never set in production.
- `/api/auth/register`, `/api/auth/login`, `/api/auth/verify-email`, and `/api/auth/resend-verification` are all rate-limited (see `rateLimit.js` above) against brute-force and mass account creation.
- There is no CSRF token — this is a deliberate, proportionate call for this app's scope: `cors()` runs without `credentials: true`, so a cross-origin fetch can't carry the cookie, and `sameSite: lax` blocks it from cross-site non-GET requests too. Don't loosen the CORS config to allow credentialed cross-origin requests without adding real CSRF protection at the same time.
- Existing boardgames created before this feature landed have `userId = NULL` (orphaned) — they won't appear for any user via `readAllByUser`. Nothing auto-assigns them; if you need to attach them to an account, do it with a one-off script/SQL against `data/boardgames.db`.
- Password reset (`/api/auth/forgot-password`, `/api/auth/reset-password`) never reveals whether an email is registered — same `200` response either way; only sends the email (and creates the reset token) when the account actually exists. Resetting the password invalidates every existing session for that user (`sessionsRepository.removeAllForUser`), not just the one that requested the reset.
- **Email verification gates registration**: `POST /register` creates the user row (or reuses an existing *unverified* one, see below) but does **not** start a session or set the `sid` cookie — it only emails a 4-digit code and responds with `{ email, message }`. The account only becomes usable once `POST /verify-email` is called with the matching code, which is the point where `usersRepository.markVerified` runs and a session is finally created. `POST /login` checks `emailVerifiedAt` after the password check and responds `403 { error, needsVerification: true, email }` for a correct password on an unverified account — the frontend's `request()` in `api.js` copies `needsVerification`/`email` onto the thrown `Error` so `handleLogin`'s `catch` can route straight into the verify screen instead of showing a generic error. Re-registering the same not-yet-verified email (e.g. typo'd or lost the email) doesn't `409` — `register` detects `existing.emailVerifiedAt` is falsy, updates that row's name/password in place, and issues a fresh code, so there's no dead-end account with no way to receive a new code. `resend-verification` (`{ email }`) follows the same generic-response pattern as `forgot-password` — same `200` message whether or not the account exists or is already verified — and is a no-op (no email, no new code) for a verified account.
- **Admin role**: every user has a `role` (`'user'` or `'admin'`). Exactly one account becomes admin automatically — the very first one ever created — via whichever of the two mechanisms in `migrate.js`/`usersRepository.create()` above applies (the migration backfill for a database that already had users, the `COUNT(*) === 0` check in `create()` for a brand-new one); there is no signup flow or env var for it. From then on, the only way roles change is through the admin panel itself (`PATCH /api/admin/users/:id/role`, gated by `requireAdmin`), and an admin can't change their own role through it (see `admin.controller.js` above) — so there's always at least one admin able to promote/demote others, short of directly editing the database. `toPublicUser` includes `role` in every auth response (`/login`, `/me`, `/verify-email`, etc.) — the frontend uses it purely for UI (show/hide the "Admin" tab); the real gate is server-side (`requireAdmin` on every `/api/admin` route).

### Frontend (`public/`, no build step, native ES modules)

- `index.html` — markup only. Three top-level regions inside `.container`: the always-visible `.brand-header` (includes the `#userBadge` shown only when authenticated), `#authView` (login/signup/forgot-password/**verify-email**, shown when logged out), and `#appView` (the tab nav + panels — Cadastrar, Coleção, Sortear, Perfil, and (admins only) Admin — shown when logged in). `main.js` toggles these three via the `hidden` attribute. `#adminTabBtn` additionally starts `hidden` in the markup itself and is only un-hidden by `showAppView` for an admin — the native `hidden` attribute is safe here since `.tab-btn` sets no `display` of its own (contrast the gotcha below, which is why `.user-badge` needed a CSS override and this doesn't). `#verifyForm` is a fourth `.auth-form` alongside login/signup/forgot — unlike those, it's never reached via an `.auth-toggle__btn` (there's nothing to toggle to it from), only programmatically after a successful signup or an unverified login attempt, same as `forgot` already works.
- `reset-password.html` + `js/reset-password.js` — standalone page for the "esqueci minha senha" email link (`?token=...`). Deliberately separate from `index.html`/`main.js` rather than folded into the auth-view state machine, since it's reached from outside the app (an email link) and has nothing to do with the logged-in/out flow. Email **verification** is the opposite case — it's a continuation of the signup the user is already mid-flow on inside the SPA (not reached from an outside link), so it's a `.auth-form` state (`verify`) like the others instead of a separate page.
- `css/tokens.css` — design tokens (color, type, spacing, radius, shadow) as CSS custom properties. `styles.css` imports it via `@import`.
- `css/styles.css` — all component/layout styles, built on the tokens. **Gotcha**: an element toggled via the native `hidden` property/attribute only actually hides if no author CSS rule sets `display` on that same selector (or a class it carries) — author-origin CSS always wins over the browser's default `[hidden] { display: none }` UA rule, regardless of specificity or source order. This bit `.user-badge` for real (`display: flex` kept the "Sair" button visible on the logged-out screen even with `hidden` set from JS); fixed with an explicit `.user-badge[hidden] { display: none }` override. Before adding `hidden`-attribute visibility toggling to a new element, check whether its class already sets `display` — if so, either add the same `[hidden]` override or (preferred, and what the rest of the app does) toggle a class like `.is-active` instead of the attribute.
- `js/api.js` — thin `fetch` wrapper; the only module that talks to the network. `api.auth.*` covers `me`/`register`/`login`/`logout`/`updateProfile`/`verifyEmail`/`resendVerification`/`forgotPassword`/`resetPassword`; `api.admin.*` covers `listUsers`/`updateUserRole`; `api.bgg.*` covers `search`/`getDetails`. Errors thrown from `request()` carry `.status` so callers can special-case `401`, plus (when present in the JSON error body) `.needsVerification`/`.email` so `handleLogin` can special-case an unverified account without a second round-trip.
- `js/render.js` — pure DOM-templating functions (game list, stats, empty state, result ticket, admin user list). Escapes all user-provided strings via `escapeHtml`.
- `js/dice.js` — the dice-roll animation (decorative; the drawn game comes from the API, not from the die face).
- `js/icons.js` — inline SVG icon strings, reused by `render.js` and inlined directly in `index.html` for the header mark.
- `js/spine.js` — deterministic category → color-index hash used for the game-card spine color.
- `js/toast.js` — toast notifications.
- `js/main.js` — orchestration only: view switching (`showAuthView`/`showAppView`), tab switching, event wiring, calling `api`, passing results to `render`. `handleAuthError(err)` is the shared 401 handler — call it in every `catch` for an authenticated request so an expired session bounces the user back to `#authView` instead of failing silently. `switchAuthMode('login' | 'register' | 'forgot' | 'verify')` toggles between the four `.auth-form`s via the `.is-active` class (not `hidden` — see the CSS gotcha above).
  - **Email verification**: `pendingVerificationEmail`/`verifySource` (module state) track the email being verified and which form triggered it (`'register'` or `'login'`) — set by `enterVerifyMode(email, source)`, which fills `#verifyEmailLabel`, clears just `#verifyCode`, and switches to it. Two paths lead there: `handleSignup`, after a successful `api.auth.register` (which no longer logs the user in — see Auth model), and `handleLogin`'s `catch`, when the thrown error carries `err.needsVerification` (a correct password on an unverified account). Neither `handleSignup` nor the login error path resets its own form before switching away — deliberately, so `#signupForm`/`#loginForm` still hold what the user typed. `#authToggle` (the Entrar/Criar conta pill) is hidden in verify mode (`.auth-toggle.is-hidden`, toggled in `switchAuthMode` — can't use the `hidden` attribute here, same CSS-wins-over-UA-default gotcha as `.user-badge` above, since `.auth-toggle` already sets `display: flex`) since neither option is a valid action mid-verification; `handleBackFromVerify` (the "Voltar" button) calls `switchAuthMode(verifySource === 'login' ? 'login' : 'register')` to return to whichever form is still holding the user's data — e.g. to fix a typo'd e-mail before resubmitting. `handleVerifyEmail` calls `api.auth.verifyEmail({ email: pendingVerificationEmail, code })` and, on success, resets both `#verifyForm` and whichever form `verifySource` points at, clears `pendingVerificationEmail`/`verifySource`, and calls `showAppView(user)` exactly like a normal login — verification *is* the last step of login for a brand-new account. `handleResendCode` calls `api.auth.resendVerification` with the same pending email; there's no client-side cooldown on it, only the server-side rate limiter. The `#verifyCode` input has its own `input` listener stripping non-digits and capping length to 4 client-side (the server still validates independently) — no library, just `e.target.value.replace(/\D/g, '').slice(0, 4)`. There's deliberately no persistence of `pendingVerificationEmail`/`verifySource` across a page reload — losing it just drops the user back to the login form, and logging in again re-triggers the same `needsVerification` path with a working "Reenviar código" button, so there's no dead end.
  - **BGG search**: `#bggSearchInput`/`#bggSearchBtn` above the register form (Enter key or button both trigger `handleBggSearch`) call `api.bgg.search`, then `renderBggResults` (in `render.js`) lists the matches; clicking one calls `handleBggSelect(id)` → `api.bgg.getDetails` → fills `name`/`minPlayers`/`maxPlayers`/`duration`/`category`/`imageUrl`/`minAge` directly on `registerForm` and calls `updateImagePreview` (see below) since setting `.value` programmatically doesn't fire the `input` event that would normally trigger it. Purely a form-filling shortcut — the user still reviews/edits before submitting, and still has to click "Cadastrar"/"Salvar alterações" themselves; nothing is saved by picking a BGG result. Works the same in create and edit mode, no special-casing.
  - The "Cadastrar" tab doubles as the edit form: `editingGameId` (module-level state) tracks whether `registerForm` is in create or edit mode; `enterEditMode(game)`/`exitEditMode()` toggle the panel title, submit button label, and the "Cancelar edição" link, and `handleRegisterSubmit` branches between `api.create`/`api.update` based on it. Switching to any other tab implicitly cancels an in-progress edit. `updateImagePreview(url)` shows/hides `#imagePreview` next to the `imageUrl` field — called from `enterEditMode` with the game's existing `imageUrl` (if any), from `exitEditMode` to clear it, and live on every `input` event on the field itself (with an `error` listener on the `<img>` hiding the preview if the URL doesn't actually load). The "Sortear" tab's `#filterCategory` dropdown is repopulated (`populateCategoryFilter`) every time that tab is opened, from the distinct `category` values in `api.list()` — there's no dedicated categories endpoint, this is derived client-side (shared with the collection filter below via `categoryOptionsHtml(games, selectedValue)`). `handleDraw` reads `#filterPlayers`/`#filterAge`/`#filterCategory` and passes them to `api.drawRandom(filters)` (server-side filtering, since we only want one result) — filter values persist across draws (not cleared automatically).
  - **Collection filters** (name/players/age/category, on the "Coleção" tab) are filtered client-side instead, since the whole list is already in memory: `allGames` (module state) holds the last `api.list(true)` response — `loadGames()` always fetches with `includeDeleted=true` so soft-deleted games are available to the "Incluir excluídos" checkbox (`#filterListShowDeleted`) without a second round-trip when it's toggled. `applyListFilters()` re-derives the visible list from it via `gameMatchesFilters(game, filters)` (which hides `deletedAt`-set games unless `filters.showDeleted` is true) and re-renders both the list and the stat tiles from the filtered subset (so the stats reflect what's currently shown, not the whole collection) — no network round-trip per keystroke. `gameMatchesFilters`'s players/age logic intentionally mirrors `boardgamesRepository.randomOneByUser`'s SQL filtering (a game missing `minPlayers`/`maxPlayers`/`minAge` isn't excluded by that specific filter) — keep the two in sync if you change one. `populateListCategoryFilter()` derives its options only from games matching the current showDeleted state, so the dropdown never offers a category that would yield an empty result. `loadGames()` refetches `allGames` and calls `applyListFilters()` (not a plain re-render) so edits/deletes elsewhere are picked up while current filter values are preserved. Deleted games render with reduced opacity and an "Excluído" badge (`renderGameList`/`gameCardTemplate` in `render.js`) and swap the edit/delete action buttons for a single "Reativar" button (`handleRestore` → `api.restore`) instead, since edit/delete would both 404 against an already soft-deleted row.
  - **Documents list** uses the same "stage locally, reconcile on save" pattern as the game form itself: `currentLinks` (module state, `{ key, id, label, url }[]`) is what the UI renders and edits — `key` is a client-generated `crypto.randomUUID()` so unsaved rows (`id: null`) can still be added/removed before the game is even saved. `originalLinkIds` snapshots which link ids existed when entering edit mode. On submit, `reconcileLinks(gameId)` diffs `currentLinks` against that snapshot: anything without an `id` gets `api.createLink`'d, anything from the snapshot no longer present gets `api.removeLink`'d. This only runs *after* the game itself is created/updated (a new game has no id to attach links to until then).
  - **Admin panel** (`#tab-admin`, admins only): `switchTab('admin')` calls `loadAdminUsers()`, which fetches `api.admin.listUsers()` fresh every time the tab is opened (no client-side cache like `allGames` — this list is small and rarely needs the same no-round-trip-per-filter treatment). `renderAdminUsers` (in `render.js`) renders one row per user with a `<select class="role-select">` for their role; changing it fires `handleChangeUserRole(userId, role)` → `api.admin.updateUserRole` → `loadAdminUsers()` again regardless of success or failure, which both confirms the change and snaps the `<select>` back to the real value if the request was rejected (e.g. trying to change your own role) — no separate revert-on-error code path needed. The admin's own row disables its `<select>` client-side (`user.id === currentUserId`) purely as a UX hint; the actual rule is enforced server-side in `admin.controller.js`.

### API surface

**Auth** (`/api/auth`)
- `POST /register` — `{ name, email, password }` (password min 6 chars). Creates the user as unverified (or reuses an existing unverified row for the same email), emails a 4-digit code, and responds `201 { email, message }` — **does not** start a session or set the `sid` cookie. `409` only if the email belongs to an already-*verified* account.
- `POST /login` — `{ email, password }`. Generic `401` on any password/email mismatch (doesn't reveal which field was wrong). `403 { error, needsVerification: true, email }` if the password is correct but the account hasn't completed `/verify-email` yet.
- `POST /logout` — clears the session (DB row + cookie).
- `GET /me` — current user (requires auth).
- `PATCH /me` — `{ name, currentPassword?, newPassword? }` (requires auth). `newPassword` requires a correct `currentPassword`. Email is intentionally not editable here — `usersRepository.updateName` only ever touches `name`; the profile form's email input is `readonly` and the controller ignores any `email` sent in the body.
- `POST /verify-email` — `{ email, code }`. `400` if the email/code shape is wrong, the account doesn't exist, is already verified, has no pending (or an expired) code, or the code doesn't match. Each wrong-code attempt increments `email_verifications.attempts`; after `MAX_ATTEMPTS` (5) the code is deleted and the client must call `resend-verification`. On success: marks the user verified, deletes the code, **starts a session and sets the `sid` cookie** — this is the only path that actually logs in a newly-registered user.
- `POST /resend-verification` — `{ email }`. Always `200` with the same generic message, whether or not the account exists or is already verified. Issues a brand-new code (replacing any existing one, resetting the attempt counter) and re-emails it, only when a matching *unverified* account exists.
- `POST /forgot-password` — `{ email }`. Always `200` with the same generic message, whether or not the email exists. Emails a `reset-password.html?token=...` link (1-hour expiry) when it does.
- `POST /reset-password` — `{ token, newPassword }`. `400` if the token is missing/invalid/expired. Invalidates the token and every existing session for that user on success.

**Boardgames** (`/api/boardgames`, all require auth)
- `GET /` — list the current user's games. `?includeDeleted=true` also returns soft-deleted games (with `deletedAt` set) alongside active ones; omitted/`false` behaves as before (only active games).
- `POST /` — add a game (`name` required; `minPlayers`, `maxPlayers`, `duration`, `category`, `imageUrl`, `minAge` optional). Server assigns `id` (`Date.now().toString()`), `userId` (from the session), and `createdAt`.
- `PUT /:id` — update a game's fields (same body shape as `POST`; only if it belongs to the current user, `404` otherwise). `id`, `userId`, `createdAt` are immutable.
- `DELETE /:id` — remove a game (only if it belongs to the current user; soft delete, see `boardgamesRepository.remove` above)
- `POST /:id/restore` — undo a soft delete (only if it belongs to the current user and is currently deleted; `404` otherwise)
- `GET /random` — return one random game owned by the current user, optionally filtered by query params: `players` (game's `minPlayers`/`maxPlayers` range must contain it — a game missing either bound isn't excluded by that bound), `minAge` (game's `minAge` must be `<= minAge`, i.e. "appropriate for this age"), `category` (exact match). `404` — message differs depending on whether filters were provided (`"Nenhum jogo encontrado com esses filtros."` vs. the no-games-at-all message), so the frontend can tell the two apart.
- `GET /:gameId/links` — list a game's documents
- `POST /:gameId/links` — add a document `{ label, url }` (`url` must match `/^https?:\/\//i`)
- `DELETE /:gameId/links/:linkId` — remove a document

**Admin** (`/api/admin`, all require auth **and** `role === 'admin'`)
- `GET /users` — every user (`id, name, email, role, createdAt, gameCount`), ordered by `createdAt ASC`. `gameCount` is that user's number of currently-active (non-deleted) boardgames. Never includes `passwordHash`.
- `PATCH /users/:id/role` — body `{ role }`, `role` must be `'user'` or `'admin'`. `400` for an invalid role or for `id` matching the requesting admin's own id (see Auth model above); `404` if `id` doesn't match any user.

**BGG** (`/api/bgg`, all require auth)
- `GET /search?q=` — search BoardGameGeek by name, returns up to 15 `{ id, name, yearPublished }`. `400` if `q` is empty; `503` if `BGG_API_TOKEN` isn't configured on the server; `502` if BGG itself fails/times out (also logged server-side via `console.error`).
- `GET /:id` — fetch one game's details from BGG by its BGG id (returned by `/search`), shaped to match the register form's fields: `{ name, minPlayers, maxPlayers, duration, minAge, category, imageUrl }`. `404` if BGG has no such id; `503`/`502` as above.

### Data model

**User**: `id` (UUID), `name`, `email` (unique, lowercased), `passwordHash` (`scrypt salt:hash`, never sent to the client), `createdAt`, `emailVerifiedAt` (`NULL` until `/verify-email` succeeds; accounts predating this feature were backfilled to `createdAt` at migration time, see `migrate.js` above), `role` (`'user'` or `'admin'`, defaults to `'user'`; exactly one account — the first ever created — was backfilled to `'admin'` at migration time, see `migrate.js` above).

**Email verification**: `userId` (PK, one active code per user), `code` (4-digit string), `createdAt`, `expiresAt` (15 min TTL), `attempts` (capped at 5 before the code must be resent). Never exposed via any API response — only used internally by `/verify-email` and `/resend-verification`.

**Boardgame**: `id, userId, name, minPlayers, maxPlayers, duration, category, imageUrl, minAge, createdAt` — all optional fields besides `name`, `userId` and `createdAt` are stored as `TEXT` columns, exactly as submitted (possibly `NULL`), not coerced to numbers server-side. `readAllByUser` orders by `createdAt ASC`; `randomOneByUser` uses `ORDER BY RANDOM() LIMIT 1`. Both responses include a `links` array (see below).

**Boardgame link/document**: `id, boardgameId, label, url, createdAt` — e.g. `{ label: "Regras base", url: "https://..." }`. A game can have any number; there's no "primary manual" field.

## Testing

Backend-only, integration-style, using Node's built-in `node:test` + `node:assert/strict` — deliberately no Jest/Mocha/Vitest/supertest dependency, matching this repo's general aversion to dependencies where a built-in does the job (same reasoning as `crypto.scrypt` over `bcrypt`, the hand-rolled cookie parser and rate limiter, etc.). `npm test` runs `node --test`, which auto-discovers every `tests/**/*.test.js` file and runs each one in its own child process (this matters — see isolation below).

- `tests/helpers/env.js` — must be the **first** thing a test file requires (before anything that transitively reaches `src/data/db.js`, `src/utils/mailer.js`, or `src/middleware/rateLimit.js`, whose test-mode behavior depends on env vars being set before they're first read/required). Sets `NODE_ENV=test`, clears `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`/`BREVO_API_KEY` so a developer's local `.env` can never leak into a test run, and points `DB_FILE` at a fresh `os.tmpdir()` path unique to that process (`crypto.randomUUID()`). Since `node --test` gives each test *file* its own process, and `db.js`'s client is a module-level singleton read once at first require, this gives every test file a fully isolated, throwaway SQLite database with zero risk of touching `data/boardgames.db` or production Turso data.
- `tests/helpers/testServer.js` — `startTestServer()` runs `runMigrations()` against that file's temp DB, builds the app via `createApp()`, and calls `app.listen(0)` (ephemeral port) — the returned object exposes `client()` (a minimal `fetch`-based HTTP client with an in-memory cookie jar, tracking the `sid` cookie across requests so a test can log in once and stay "logged in" for the rest of that client's calls) and `close()`. Also exports `getVerificationCode(email)`/`getUserByEmail(email)` (read straight from the temp DB — the equivalent of the manual `TURSO_DATABASE_URL='' node -e "..."` DB pokes used throughout this project's development to check codes/roles without a real inbox) and `registerAndVerify(client, opts)`, a one-call shortcut through the full register → fetch-code-from-DB → verify-email flow for tests that just need *a* logged-in user and aren't specifically testing that flow. `cleanupDbFile()` closes the sqlite client and best-effort deletes the temp file/`-wal`/`-shm` siblings in each file's `after()` hook — on Windows this can silently fail (`EBUSY`, confirmed the native binding doesn't release the file handle synchronously even right after `close()`) and leave a small leftover file in the OS temp dir; harmless and doesn't happen on Linux/macOS CI, so it isn't worth chasing further.
- `tests/auth.test.js`, `tests/boardgames.test.js`, `tests/boardgameLinks.test.js`, `tests/admin.test.js` — full HTTP-level integration tests through the real Express app (register/login/verify/resend/logout/forgot/reset, boardgame CRUD + soft delete/restore + ownership scoping, links nested-ownership, and the admin role/panel endpoints including "first user becomes admin"). `admin.test.js`'s very first test **must** register the file's first-ever user, since "first user becomes admin" is only true relative to that file's own isolated DB — every other admin test reuses that same already-logged-in client from a `before()` hook rather than trying to register a second "first" user (impossible after the first exists).
- `tests/rateLimit.test.js` — the one unit-level (no HTTP, no DB) test file, calling the `rateLimit()` middleware factory directly with mock `req`/`res` objects. Deliberately does **not** require `tests/helpers/env.js`, so `NODE_ENV` stays unset in that file's process and the real counting/429 logic in `rateLimit.js` actually runs, instead of being bypassed by the test-mode short-circuit described above.
- `tests/bgg.test.js` — two layers: pure unit tests of `parseSearchXml`/`parseThingXml` against hand-written fixture XML (no network — see `bgg.js` above for why), and HTTP-level route tests that mock the client with `node:test`'s built-in `t.mock.method(bggClient, 'searchGames', ...)`/`t.mock.method(bggClient, 'getGameDetails', ...)` rather than hitting the real BGG API. This only works because `bgg.controller.js` does `const bggClient = require('../utils/bgg')` and calls `bggClient.searchGames(...)` — i.e. keeps a reference to the whole module object and reads the method off it at call time — instead of destructuring `const { searchGames } = require('../utils/bgg')` at load time, which would capture the original function and make it unmockable from outside. `t.mock.method` auto-restores after each test, no manual cleanup needed. Follow this same module-reference pattern (not destructuring) for any future controller wrapping an external API that tests will need to mock. `tests/helpers/env.js` sets a dummy `BGG_API_TOKEN` precisely so these mocked tests exercise the real route logic instead of tripping the controller's `503` not-configured guard; one dedicated test temporarily `delete`s it (restored in a `finally`) to cover that guard specifically.
- **Convention going forward**: run `npm test` before every push (part of the commit+push-when-working convention below), and any new feature or bugfix should come with test coverage in the relevant `tests/*.test.js` file — extend an existing file for something that fits an existing area (auth, boardgames, links, admin), or add a new `tests/<area>.test.js` following the same `helpers/env` → `helpers/testServer` pattern for a genuinely new area.

## Code quality: ESLint

`eslint.config.js` (flat config, ESLint 9+/10 style) — `npm run lint` runs `eslint .`. Base is `@eslint/js`'s `recommended` config plus `eslint-plugin-security`'s `recommended` config, split across three `files` blocks with different `languageOptions`/globals: `src/**`, `server.js`, `tests/**`, and `eslint.config.js` itself are CommonJS/Node; `public/js/**` is browser ES modules. Deliberately **not** Airbnb/Standard or a formatter (Prettier) — this repo has no build step and no existing style-linting history, so a heavy opinionated config would produce a huge one-time diff for no functional benefit; `recommended` catches real bugs (undefined vars, unreachable code) without imposing style.

Two rules from `eslint-plugin-security`'s recommended set are turned off repo-wide, with the reasoning left as a comment in `eslint.config.js`: `detect-object-injection` and `detect-non-literal-fs-filename`. Both fire on any bracket-notation property access or `fs.*Sync(variablePath)` regardless of whether the key/path is actually attacker-controlled — in this codebase it never is (cookie/session lookups by hardcoded constant, `FACE_POSITIONS[face]` with `face` from a fixed die value, `db.js`'s `DB_FILE`-derived paths from env/config, never from request data). Confirmed false-positive on every instance before disabling — don't re-enable without re-auditing, and don't disable further rules from the security plugin without the same scrutiny (the rest — unsafe regex, `eval`, non-literal `require`, `child_process` — stay on and are meaningful for a Node backend).

## CI/CD pipeline

GitHub Actions (`.github/workflows/ci.yml`), three parallel jobs (`lint`, `test`, `security`), triggered on every PR targeting `main` and every push to `main`. Runs entirely on GitHub's hosted runners — no local machine involvement, no relation to any AI/Claude usage, and well within GitHub Actions' free-tier minutes for a repo this size (repo is **private**, confirmed via the GitHub API returning 404 for unauthenticated access — this matters because it rules out GitHub's own free code scanning/secret scanning, which require GitHub Advanced Security on private repos).

- `lint` — `npm ci` + `npm run lint`.
- `test` — `npm ci` + `npm test` (the suite described above).
- `security` — `npm ci` + `npm audit --audit-level=high` (fails on known high/critical vulnerabilities in dependencies) + `gitleaks/gitleaks-action` (open-source secret scanner, the free-repo-private-safe substitute for GitHub's native secret scanning).
- `.github/dependabot.yml` — weekly update PRs for both the `npm` ecosystem and `github-actions` (the workflow's own `uses:` pins) — Dependabot alerts/PRs are free regardless of repo visibility, unlike code/secret scanning.
- All three `actions/setup-node` steps use `node-version-file: package.json` (reads `engines.node`) rather than a hardcoded version, so bumping the `engines` field is the only place a Node version upgrade needs to happen.

**Workflow**: feature/fix branches → PR into `main` → all three checks green → merge. `main` itself is (or should be) branch-protected in GitHub's web UI (Settings → Branches — not doable from the repo/CLI) to require the `lint`/`test`/`security` status checks before merge, with **no required review approval** (single-maintainer project — requiring another human's review would just block every PR indefinitely). Whatever auto-deploys the app (Render, based on `.env.example`'s and `mailer.js`'s comments) should have its auto-deploy pointed at `main`; once `main` only accepts CI-green merges, that auto-deploy is safe by construction and needs no separate gating step in the workflow itself.

Complementary but **not** part of the automated pipeline: periodically running `/code-review security-review` or `/code-review ultra` (Claude Code features already available in this environment) before/after touching anything auth-related — this uses Claude/Anthropic usage on demand, unlike everything else on this list, and is a manual practice, not a CI gate.

## Design system

Tabletop/felt-table visual identity, tokenized in `public/css/tokens.css`:

- **Color**: deep felt green (`--felt`) as the page surface, cream cardstock (`--card`) for panels/cards, `--ember` as the one primary-action accent. `--gold`, `--teal`, `--mustard`, `--plum` are secondary/spine accents — `spine.js` hashes a game's category to one of them (`spine-0`…`spine-4`) rather than assigning colors by hand.
- **Type**: `--font-display` (Fraunces) for headings/titles, `--font-body` (Inter) for UI copy, `--font-mono` (IBM Plex Mono) for stats/numbers — keep that role split when adding UI.
- **Signature element**: the "Sortear" tab draws a game via a flip-style die animation (`dice.js`) that resolves into a perforated raffle-ticket card (`.ticket` in `styles.css`) — this only appears once, on the felt background (not nested inside a cream `.panel`), so its punched-hole notches (`.ticket__perf::before/::after`, colored `var(--felt)`) blend correctly. If you rewrap `#drawStage` inside a `.panel`, update the notch color to match or the illusion breaks.
- **Auth screen**: reuses `.panel` (cream card) with an `.auth-toggle` pill switcher between the login and signup `.auth-form`s — same visual language as the tab system, not a separate style. The `forgot`/`verify` forms share the same `.panel`/`.auth-form` shell but aren't wired to the pill switcher (reached only via links/redirects, see `main.js` above). The verify form's `.code-input` (large, centered, letter-spaced `--font-mono`) is the one auth input styled differently from the rest, to read as a distinct "type a code" affordance rather than a normal text field.
- **Documents**: `.doc-chip` (small teal pill, `--font-mono`, document icon) is how a game's links surface passively on the game-card and the draw ticket — read-only, opens in a new tab. `.link-row` (in the register/edit form) is the editable counterpart, cream-soft background with a label, an "Abrir ↗" link, and a remove button — deliberately a different, heavier treatment since it's an editing control, not just a display.

### Conventions to preserve

- Keep the layered backend structure (routes → controllers → repository) and the modular frontend (`public/css/*`, `public/js/*`) — don't collapse back into single-file `server.js`/`index.html`, this structure exists specifically to support future features.
- Data access goes through the repositories in `src/data/` only; controllers never touch `db.js`/`@libsql/client` directly. Every repository function is `async` — don't reintroduce synchronous `node:sqlite`-style calls.
- Deploying somewhere without persistent disk (serverless/ephemeral filesystems, or a free-tier host like Render) means the local-file fallback in `db.js` won't survive a restart — set `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` in that environment so `db.js` points at Turso instead. Nothing else in the code needs to change to switch between the two.
- Every new authenticated route must scope its data access by `req.user.id`, mirroring `boardgames.controller.js` — never trust a client-supplied user id.
- User-facing strings and UI copy are in Portuguese (pt-BR), written in an active, direct voice (e.g. toast/error copy says what happened and what to do, not a generic "erro ao..."); match that when adding new UI text or API error messages.
- No bundler/build step by design — frontend JS relies on native ES module `import`/`export` served as static files. If you add a module, reference it with an explicit relative path (and `.js` extension) from its importer.
- Don't send outbound email over SMTP — use an HTTP-based provider API instead (see `mailer.js`). SMTP ports are frequently blocked on free-tier hosts, and the failure mode is a silent hang (no error, no timeout by default), not a clean rejection — it's a bad category of bug to reintroduce.
- **Commit and push automatically once a feature is implemented and verified working** — the user has opted into this for this project specifically, overriding Claude Code's general default of only committing when explicitly asked. Still use good commit hygiene (one feature per commit, descriptive message, no unrelated changes bundled in) and still ask first for anything destructive/irreversible (force-push, history rewrite, etc.) — this only covers the normal "commit + push the working change" step. **Since the CI/CD pipeline above (added 2026-08-04), this means pushing a feature/fix branch and opening a PR into `main`, not pushing straight to `main`** — `main` is meant to only move via CI-green merges. No `gh` CLI is available in this environment as of that date, so "open a PR" means pushing the branch and handing the user the compare URL (`https://github.com/MateusAraujo9/sorteador-bg/compare/main...<branch>?quick_pull=1`) to click, unless `gh` becomes available later.
- **Run `npm test` and `npm run lint` before every push, and cover new work with tests** — also user-opted-in specifically for this project (lint requirement added alongside the CI pipeline, same date). Every new feature or bugfix should land with test coverage in `tests/` (see Testing above) — extend an existing `tests/*.test.js` file if the change fits an existing area, add a new one following the same pattern otherwise. Don't push if `npm test` or `npm run lint` is failing; fix it (or the code) first — the CI pipeline enforces the same two checks (plus `npm audit`/gitleaks) server-side, so catching it locally first just saves a round-trip.
